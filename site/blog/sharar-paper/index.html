Sharar: Fast Agentic Inference on Unified-Memory Devices

Paper · November 4, 2026

On a unified-memory device, the model and every agent's history share one memory. Sharar co-designs the model, its memory, and its decoding so many agents run fast on a single DGX Spark.

The idea in a minute

Local agents extend long histories, pause for tools, and run side by side. On a unified-memory device such as the DGX Spark, the weights, the active requests, and every saved history share one 128 GB pool, and every generated token streams the weights through limited bandwidth. Sharar attacks both limits at once.

Model surgery. Edit the trained model to fit the hardware: 3-bit weights, INT8 recurrent state, and a 2-bit draft head, so each token reads fewer bytes.

Unified-memory management. Keep every agent's state across turns, spilling it to the SSD when GPU memory runs out, so a returning agent resumes instead of recomputing.

Adaptive speculation. Share experts across drafted tokens and draft only as far as acceptance pays for, so each weight read yields more tokens.

Model surgery

Decoding one request is bound by memory bandwidth, so the fastest token is the one that reads the fewest bytes.

Three-bit weights

Each group of 32 weights snaps to an 8-entry FP8 codebook, so each weight is stored as a 3-bit index. The kernel looks up the codes and feeds FP8 tensor cores directly.

Eight values per group, three bits per weight. Codes take 3 bits and each group of 32 adds one 8-bit scale: 3 + 8/32 = 3.25 bits per weight. The codebook here is fitted to the group for illustration.

Two-bit draft head

The drafter's output head scores every token in the vocabulary and is the largest matrix the drafter reads. A 2-bit copy is cheap but noisy, so Sharar uses it only to shortlist candidates, then rescores the shortlist in FP8.

Unified-memory management

Agents take turns. By the time an agent returns, other agents have usually pushed its state out of GPU memory.

SSD session cache

Discard an evicted agent's state and its next turn recomputes the whole context. Sharar spills the KV cache, recurrent state, and draft state to the SSD instead, and reads them back when the agent returns.

Adaptive speculation

A drafter proposes several tokens and the target checks them in one pass. Sharar makes each of these rounds cheaper and sizes it to what will be accepted.

Expert sharing

In a mixture-of-experts layer, verifying drafted tokens loads every expert any of them picked. Sharar gives the round a shared expert budget, so it reads fewer weights.

Quick start

Install uv, then:

# the repository opens with the paper
git clone https://github.com/abdelfattah-lab/sharar && cd sharar
uv sync
uv run sharar serve 27b          # Qwen3.8-27B on http://127.0.0.1:30001
uv run sharar serve flashnext    # Qwen3.8-Flash-Next (125B MoE)
uv run sharar launch claude      # point a coding agent at it

OpenAI- and Anthropic-compatible APIs, 262K context, one Spark or two over ConnectX. Add --exact for the model's own outputs.
