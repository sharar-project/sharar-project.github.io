Local agents keep extending long histories in the same memory that holds the model. Sharar decides what stays resident, what survives between turns, and what each accepted token costs.

Three surgeries

Model surgery

Calibrated 3-bit weights for dense projections and routed experts, packed so FP8 tensor cores consume them directly.

  • 3.25 bits/weight: 8-entry FP8 codebook, scale per 32 weights
  • NVFP4 KV cache, INT8 recurrent state
  • 2-bit draft head with top-16 rescoring
work kept across turns ↑

Unified-memory hierarchy

Evicted conversations are demoted to the SSD instead of discarded, so an agent's next turn resumes rather than recomputes.

  • Whole continuations: KV pages, recurrent snapshots, draft state
  • One ledger for GPU pools, staging buffers and page cache
  • Sparse lookup tables (PLE) served from NVMe
work per accepted token ↓

Adaptive speculation

Each draft-verify round is sized and priced: draft as deep as acceptance pays for, and keep verify batches cheap.

  • Adaptive draft depth from observed acceptance
  • Optional relaxed verification (top-k, logit margin)
  • Shared routed-expert budget in verify batches

Sharar serves three profiles. exact keeps the model's own outputs; fast (default) and throughput add named lossy approximations. The tags in the figure above say which steps are which.

Try it · expert sharing

A verify batch reads the union of every token's experts

In an MoE layer each token picks its own top-k experts, and verifying a batch of draft tokens must load every expert any of them chose. Sharar gives the batch a shared budget: each token's top choice is guaranteed, the remaining slots go to the experts with the most routing mass, and every token's second choice is taken from inside that set. Fewer distinct experts means fewer weight bytes per round.

Try it · adaptive drafting

Draft only as deep as acceptance pays for

Each extra draft token costs one more draft step and one more verification row. Sharar keeps a per-request estimate q of how often a drafted position is accepted, and picks the depth that maximizes expected tokens per unit of round time:

d* = argmax1≤d≤dmax (Σj=0..d qj) / (1 + c·(d − 1))

Move the sliders. High-acceptance text (code, repeated tool output) earns deep drafts; uncertain text earns shallow ones. Under exact verification this changes speed only, never the output.

Model surgery · draft head

A 2-bit draft head that still agrees with FP8

The draft model's vocabulary head is the largest matrix it reads every step. Sharar stores it in 2 bits and rescores the top-16 candidates in higher precision, which recovers agreement where it was lost: on uncertain tokens, where the naive 2-bit head picks a different token half the time. Only the drafter changes, so the target still decides every token.

Unified-memory hierarchy · SSD tier

When open context outgrows the GPU, demote it to the SSD

192 agent conversations open at once, 32 running. Once their contexts exceed the KV that fits beside the weights, other engines drop prefixes and recompute them on the agent's next turn. Sharar writes complete continuations to NVMe and reads them back, so turns keep starting from cache. During the burst, median time to first token is 4.0 s on Sharar against 167 s on vLLM, 42× lower.

Quick start

Serve a model on one Spark

Install uv, then:

# the repository opens with the paper
git clone https://github.com/abdelfattah-lab/sharar && cd sharar
uv sync
uv run sharar serve 27b          # Qwen3.8-27B on http://127.0.0.1:30001
uv run sharar serve flashnext    # Qwen3.8-Flash-Next (125B MoE)
uv run sharar launch claude      # point a coding agent at it

OpenAI- and Anthropic-compatible APIs, 262K context, one Spark or two over ConnectX. Add --exact for the model's own outputs.
