Repairing a Quantized LLM using Weight Space Programming

Blog · November 2026

Yahya Emara, Chi-Chih Chang, Mohamed Abdelfattah

Cornell University

Poorly calibrated + edits Well-calibrated + edits BibTeX

We quantize a lot of models. Usually it goes like this: take a checkpoint, squeeze it down to a few bits per weight, watch some benchmark fall off a cliff, then spend a week poking at the calibration set until it mostly comes back. It works, kind of. But it always feels like fixing a watch by shaking it.

So we tried something more direct, inspired by weight-space programming. We handed a broken 3-bit checkpoint to an LLM agent, gave it a Python session with the weights loaded, and asked it to find what went wrong and fix it, by editing the weights directly and without fitting them to any data. On Nemotron-3.5-Lightning-30B-A3B it found two broken matrices out of 5,959, edited about one weight in 120,000, and closed most of the gap to the NVFP4 release.

How quantization usually works

The standard recipe is calibration plus post-training quantization (PTQ): run a small calibration set through the model, then let a method like GPTQ1 or AWQ2 use those activations to decide how to round the weights. You get a 2–4-bit model that fits on smaller devices and decodes faster, since decoding is memory-bound.

Some bitter lessons

If you have pushed PTQ to aggressive bit widths, you have probably hit all three of these:

Calibration data matters way more than it should. Finding the right mix of domains, lengths and formats is basically alchemy. A blend that helps math hurts code, and nobody can tell you the right one ahead of time.

Aggressive formats leave a gap. At 3 bits and below, even good methods lose accuracy, and the loss is lumpy across tasks.

Often you don't have the recipe. If all you get is a released checkpoint, you don't know what it was trained on, so you can't build a calibration set that matches. For the model in this post, the only source we had was the NVFP4 release.

All three treat the quantized model as a black box you can only re-run with different inputs. We wanted to open the box.

What if the LLM fixes the model itself?

Our starting point is Sparks of Weight-Space Programming3, by Takehi et al.: frontier LLMs can read and write neural network weights directly. In their Experiment 8 the agent makes Qwen3.5-0.8B much better by fixing its reasoning loops, editing 0.016% of its weights, with no gradients and no training loop.

Repairing a quantized checkpoint looked like a natural fit, with one big advantage: we know what every weight is supposed to be, because we have the higher-precision source to compare against. We gave the agent this brief:

This 3-bit checkpoint should behave like the NVFP4 model. Find what is broken and fix it inside the 3-bit format. You may run the model and read its weights and activations; you may not fit weights to data (no GPTQ, no least-squares refits, no training).

The agent starts from the finished 3-bit checkpoint, not from NVFP4. The NVFP4 weights are its reference: they tell it how far the 3-bit model is from where it should be, and every new 3-bit value it writes is the NVFP4 weight rounded again under a different rule. Whoever quantizes a model has its source weights, so this needs nothing extra.

The repair loop. The agent edits the 3-bit weights directly. After each edit it scores the model on validation data: KL to NVFP4 on held-out chat math, code and prose, perplexity, MMLU-val, GSM8K-dev, and how well it predicts NVFP4's own answers. It keeps the edit if those improve without regressions and reverts it otherwise. Test sets are never used.

Case study

How the agent found the defect, and how it fixed it

Everything here was done by reading tensors and printing numbers in a Python session. We follow the well-calibrated checkpoint, where the agent first found the defect. The same two rules later repaired the poorly calibrated checkpoint too.

1. Measure the gap

Both models read the same held-out text, and at every token we compare their next-token distributions with KL divergence. Lower means closer to NVFP4.

Code and prose diverge about 14× more than chat math. Some gap is expected: even after every repair it is still about 7×. But this gap was twice that, which pointed to a specific defect that hurts code and prose more than chat.

2. Localize the damage

The model has thousands of quantized matrices, too many to read one by one, so the agent narrowed down in two passes. First it restored one kind of matrix to NVFP4, in every layer at once, and measured how much of the KL gap disappeared. Then, within the worst kind, it restored one matrix at a time.

Restoring the Mamba in_proj matrices removes much of the chat-math gap but little of the code and prose gap, so the agent followed out_proj.

One matrix stands out: the Mamba output projection (out_proj) in layer 4. Restoring it alone removes about two thirds of the code and prose gap.

3. Diagnose the damage: Activation outlier

First, what this matrix does. At every token the layer computes Y = XW. Each column of X is an input channel, and each input channel has its own row of W: the weights it is multiplied by. Each column of W, and the matching column of Y, is an output channel: one output of the layer. (We write W with inputs as rows; PyTorch stores it transposed.)

The weights alone don't say which ones matter, because each weight's error is multiplied by its input. So the agent ran the NVFP4 model on a few dozen held-out sequences, recorded the input X to this matrix, and scored every weight by its squared error, stored value minus its NVFP4 value (the reference weight), times the mean of x² over the recorded tokens, where x is the value of the weight's input channel on a token. We call the result the weight's output error. It scores each weight on its own, so it ignores how errors in different rows can offset each other.

The output error comes from a few input channels. Just four of them cause over 80% of it, and one alone causes 71%; no other channel causes more than 6%.

That one channel is an activation outlier. On the first three tokens it reaches 20 to 60, while a typical channel stays below 0.01; after that it is as quiet as the rest. We call it the outlier input (input channel k of X). The outlier is in X, not in W: row k of W, the row that multiplies the outlier input, holds ordinary weights. Other language models show similar huge values in a few channels on the first tokens, known as massive activations5 and linked to attention sinks4.

The input X to layer 4's Mamba out_proj, channel × token. Mean |x| over the held-out sequences, first 64 tokens, channels pooled in blocks of 16 (max), log scale. The outlier input spikes on the first three tokens; every other channel stays below 2.

A large activation is not a problem by itself. It becomes one when the weights it multiplies are quantized with error: that error is scaled by the activation, so on those three tokens it is amplified into every output channel.

outlier inputrow k, the row of W it multiplieserror in Y: row k's rounding error times the outlier input
(Q(w)−w)x =Δ·RoundErr(wΔ)·x

How one input channel amplifies weight error. The outlier is in the input: one channel of X is large on the first three tokens. The weights in row k of W have ordinary rounding errors, but those are the errors multiplied by the outlier input, so on those tokens they show up in every output channel of Y. Same equation as AWQ2, in our notation: Q(w) is the stored weight, Δ a scale shared by a group of 32 weights, and RoundErr the rounding error in units of Δ (all in step 4).

This is the principle behind AWQ2, which calls such weights salient: which weights matter is decided by the activation distribution, not by the weights themselves. The model needs the large activation; what is broken is how the weights it multiplies were quantized.

4. Fix 1: No rounding error in row k

In the equation from step 3, the cost of a weight's rounding error is that error times its input. The rounding errors in row k are ordinary in size, but they are the ones multiplied by the outlier input. The model needs that input, so fix 1 removes the rounding error on those weights instead.

How a group is quantized. Each column of W is cut into groups of 32 consecutive input channels, and each group has one scale Δ. Each reference weight w in the group is divided by Δ and mapped to the nearest point of a fixed grid L of 8 levels (no level at zero; the largest in magnitude is qmax). The stored weight ŵ is that level times Δ:

Q(w)=Δ·roundL(wΔ) RoundErr(wΔ)=roundL(wΔ)−wΔ

With plain rounding, ŵ = Q(w), so a weight's error ŵ − w is Δ · RoundErr(w/Δ), the term in the step-3 equation. Quantizing a group means choosing its Δ first, then mapping all 32 weights with it. GPTQ rounds W one row at a time and, after each row, updates the rows it has not rounded yet (step 5); we write w̃ for a weight after those updates. GPTQ chooses Δ with the min-max rule, so that the group's largest weight in magnitude maps to qmax (i runs over the 32 weights of the group):

ΔGPTQ= maxi|w˜i|qmax

In each output channel, row k's weight wk is tiny next to the other 31 weights in its group, so wk/Δ falls well below the smallest level in magnitude and is rounded up to it. That error is no bigger than other weights' errors, but it is the one multiplied by the outlier input.

Fix 1 keeps one Δ per group and the same mapping; it only changes how Δ is chosen, and only in the groups that contain a weight of row k, one per output channel. Instead of the min-max rule, it takes the scales that map wk exactly onto a level, wk/Δ = ℓ, one for each level ℓ with the sign of wk. Of these candidate scales, 𝒞, it keeps the one under which the other 31 weights wi are mapped with the least error (QΔ is Q with scale Δ):

𝒞={wkℓ:ℓ∈L,ℓwk>0} Δfix 1= arg⁡minΔ∈𝒞 ∑i≠k (QΔ(wi)−wi)2

Every candidate maps wk onto a level, so its rounding error is zero: Q(wk) = wk, up to the precision in which Δ itself is stored. The result is a different scale for the group, not a new maximum: in the example group, the best candidate maps wk to the smallest level, which shrinks Δ to about a fifth of GPTQ's. Choosing Δ fits nothing to data: it uses only the reference weights and the grid. In W, this touches only the groups that contain a weight of row k:

The price. The new Δ is smaller, so the largest weights in the group now map beyond qmax and are clipped to it. That costs little: their inputs are tiny, and the equation scales each error by its input. The group's output error falls 18×.

Across the matrix. The rule runs once per output channel, on the one group that contains row k's weight: it replaces that group's Δ and re-maps its 32 weights. Across row k, the stored weights go from several times too large to matching the reference:

5. Fix 2: Remove GPTQ's compensation

Fix 1 alone cut prose KL threefold, but chat math got worse: GSM8K accuracy on the validation split fell from 93.1% to 85.6%. The cause was in other rows of the same matrix.

How GPTQ compensates. GPTQ rounds W one row (input channel) at a time, in a fixed order. It minimizes ‖XW − XŴ‖² on its calibration text, where Ŵ holds the stored weights, so after each row it updates the rows it has not rounded yet to reduce the error in Y it just made. These updates are usually small. Row k is the exception: its rounding error is amplified by the outlier input, so GPTQ moved some later rows a lot to offset it, namely the rows whose inputs move together with the outlier input on the calibration text. We call these rows compensating rows, and how far GPTQ moved their weights before rounding them, w̃ − w, their compensation.

Why it breaks after fix 1. Fix 1 removes row k's rounding error. The compensation now has nothing to offset, so it becomes error in Y itself.

What fix 2 changes in W. GPTQ quantizes the rows from top to bottom. (a) Row k multiplies the outlier input, so its error is amplified; GPTQ cancels most of it, on its calibration text, by moving later rows off their reference values. (b) Fix 1 removes row k's error, so there is nothing left to cancel and the moved rows' error shows up in the output. (c) Fix 2 re-rounds the moved rows to nearest. Finding them needs no data. For every row, the agent compared how far GPTQ's stored weights are from the reference weights with how far plain round-to-nearest would be under the same scales. In an ordinary row the two are about the same. In this matrix, 87 of the 4,096 rows are at least 3× farther, up to 14×, because of the compensation; we take the rows past this 3× cutoff as the compensating rows. All of them come after row k in GPTQ's order.

Fix 2 removes the compensation. The compensation is held in the stored levels, not in the scales. GPTQ stored each weight of a compensating row as ŵ = Q(w̃), the level nearest to the moved weight. Fix 2 keeps every Δ and re-rounds each of those weights from its reference value instead, ŵ = Q(w): the level nearest to w, which no longer carries the move. Every other row keeps GPTQ's stored levels. This also drops GPTQ's small, ordinary updates on those rows; telling them apart from the compensation would need calibration data, which the fixes avoid.

Fix 1 changes some group scales and the levels in those groups; fix 2 changes only levels. Neither adds storage, so the checkpoint's size and speed are unchanged. With both fixes, GSM8K on the validation split rose to 94.7%, above where it started.

What this means for quantization

GPTQ's objective is fine. Its constraint is the problem: it fixes each group's scale from the group's largest weights before choosing levels. When a group also holds a tiny weight on a huge input, no choice of level can store it, and GPTQ falls back on offsetting the error through other weights, fitted to the calibration tokens and wrong on most others.

That makes the fix cheap: a repair pass that needs no data. Scan for compensation, find the outlier input in one forward pass, apply both fixes.

Where this goes next

The agent repeated the loop until no edit helped. On this checkpoint it kept both fixes on two Mamba out_proj matrices, plus one small scale change in an attention layer, the only edit whose scale choice reads activations. The same two fixes, unchanged, repaired the poorly calibrated checkpoint. Every edit rewrites existing quantized levels and scales, so the model keeps the same size, format and kernels.

Today, that makes agent editing a finishing pass for any quantized checkpoint, whatever quantizer produced it: it smooths over the places where the quantizer failed and improves the model without quantizing it again. All it needs is the checkpoint, the higher-precision reference, and a few prompts to read activations and validate on. And because each edit comes with a reason, it also tells you what the quantizer got wrong.

Longer term, we see this going much further. As LLMs get more capable, we expect agents, or rather swarms of them working in parallel, to quantize models with trillions of parameters themselves, starting from the full-precision weights, instead of only repairing a checkpoint after the fact.
