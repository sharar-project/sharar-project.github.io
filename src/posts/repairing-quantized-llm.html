Repairing a Quantized LLM using Weight Space Programming

Blog · November 2026

Yahya Emara, Chi-Chih Chang, Mohamed Abdelfattah

Cornell University

🤗 Poorly calibrated + edits 🤗 Well-calibrated + edits Code BibTeX

We quantize a lot of models. The usual routine is to take a checkpoint, squeeze it down to a few bits per weight, watch some benchmark fall off a cliff, then spend a week poking at the calibration set until it mostly comes back. It works, kind of. But it always feels like fixing a watch by shaking it.

So we tried something more direct, inspired by weight-space programming. We handed a broken 3-bit checkpoint to an LLM agent, gave it a Python session with the weights loaded, and asked it to find what went wrong and fix it, by editing the weights directly and without fitting them to any data. On Nemotron-3.5-Lightning-30B-A3B it found two broken matrices out of 5,959, edited about one weight in 120,000, and closed most of the gap to the NVFP4 release.

How quantization usually works

The standard recipe is calibration plus post-training quantization (PTQ). You run a small calibration set through the model, then let a method like GPTQ1 or AWQ2 use those activations to decide how to round the weights. You get a 2–4-bit model that fits on smaller devices and decodes faster, since decoding is memory-bound.

Some bitter lessons

If you have pushed PTQ to aggressive bit widths, you have probably hit all three of these:

Calibration data matters way more than it should. Finding the right mix of domains, lengths and formats is basically alchemy. A blend that helps math hurts code, and nobody can tell you the right one ahead of time.

Aggressive formats leave a gap. At 3 bits and below, even good methods lose accuracy, and the loss is lumpy across tasks.

Often you don't have the recipe. If all you get is a released checkpoint, you don't know what it was trained on, so you can't build a calibration set that matches. For the model in this post, the only source we had was the NVFP4 release.

All three treat the quantized model as a black box you can only re-run with different inputs. We wanted to open the box.

What if the LLM fixes the model itself?

Our starting point is Sparks of Weight-Space Programming3, by Takehi et al. In their Experiment 8 the agent makes Qwen3.5-0.8B much better by fixing its reasoning loops, editing 0.016% of its weights, with no gradients and no training loop.

Repairing a quantized checkpoint looked like a natural fit, with one big advantage. We know what every weight is supposed to be, because we have the higher-precision source to compare against. We gave the agent (Claude Opus 5.5) this instruction:

This 3-bit checkpoint should behave like the NVFP4 model. Find what is broken and fix it inside the 3-bit format. You may run the model and read its weights and activations; you may not fit weights to data (no GPTQ, no least-squares refits, no training).

This is the task section of the full prompt. The rest of it, with the rules, the repair loop and the evaluation harness the agent uses, is in program.md in the wsp-ptq repository.

The agent starts from the finished 3-bit checkpoint, not from NVFP4. The NVFP4 weights are its reference. They tell it how far the 3-bit model is from where it should be, and every new 3-bit value it writes is the NVFP4 weight rounded again under a different rule. Whoever quantizes a model has its source weights, so this needs nothing extra.

The repair loop. The agent edits the 3-bit weights directly. After each edit it scores the model on validation data, measuring KL to NVFP4 on held-out chat math, code and prose, perplexity, MMLU-val, GSM8K-dev, and how well it predicts NVFP4's own answers. It keeps the edit if those improve without regressions and reverts it otherwise. Test sets are never used.

Case study

How the agent found the defect, and how it fixed it

In short. One input to one matrix is huge on the first few tokens. The weights it multiplies are tiny, and the 3-bit format stores them about 5× too large, so the huge input turns a small weight error into a large error in the matrix's output. On its calibration text, GPTQ had cancelled most of that error by adjusting other weights. Fix 1 stores the tiny weights almost exactly. Fix 2 undoes GPTQ's adjustments, which fix 1 had turned into error.

The five steps

We follow the well-calibrated checkpoint, where the agent first found the defect. The same two fixes later repaired the poorly calibrated one too.

1. One matrix holds most of the damage

The agent first measured how far the 3-bit model's next-token predictions are from NVFP4's on held-out chat math, code and prose (KL divergence). Then it put quantized matrices back to NVFP4 and measured how much of that gap disappeared: first one kind of matrix across all layers, then one matrix at a time.

One matrix stands out: the Mamba output projection (out_proj) in layer 4. Restoring it alone removes about two thirds of the code and prose gap.

2. The cause: a huge input times badly stored weights

The matrix computes \(\mathbf{Y} = \mathbf{X}\mathbf{W}\). Each input channel (a column of \(\mathbf{X}\)) is multiplied by its own row of \(\mathbf{W}\), and each column of \(\mathbf{W}\) gives one output channel of \(\mathbf{Y}\).

The agent ran the NVFP4 model on a few dozen held-out sequences of chat math and prose, recorded \(\mathbf{X}\), and found one input channel that is huge on the first three tokens, around 50, while a typical channel stays below 0.01. We call it the outlier input, channel \(k\), and the row of \(\mathbf{W}\) it multiplies row \(k\). Huge values like this on the first tokens are common in language models, known as massive activations5 and linked to attention sinks4.

The input \(\mathbf{X}\) to layer 4's Mamba out_proj, channel × token. Mean \(|x|\) over the held-out sequences, first 64 tokens, log scale.

A huge input is fine on its own. The trouble is that row \(k\)'s weights are tiny, and the 3-bit format stores them badly. Take one of them: its NVFP4 value is about 0.0005, but the smallest positive value the format can store for it is about 0.0026, so that is what is stored, about 5× too large. A weight's storage error, \(\hat w - w\), reaches \(\mathbf{Y}\) multiplied by its input:

\[ \text{one weight's error in } \mathbf{Y} = (\hat w - w)\cdot x \]

where \(w\) is the NVFP4 weight, \(\hat w\) the stored weight and \(x\) its input. On those first tokens, where \(x\) is about 50, this one weight adds about 0.1 of error to its output: \((0.0026 - 0.0005) \times 50\). Later in the sequence, where \(x\) is about 0.01, the same weight adds 0.00002.

outlier inputrow \(k\), the row of \(\mathbf{W}\) it multiplieserror in \(\mathbf{Y}\): row \(k\)'s weight error times the outlier input

How one input channel amplifies weight error. On the first three tokens, row \(k\)'s small weight errors are multiplied by the outlier input, so they show up in every output channel of \(\mathbf{Y}\).

MSE in \(\mathbf{Y}\). To find which weights cause the damage, the agent measured each weight's MSE in \(\mathbf{Y}\): its error in \(\mathbf{Y}\) (the equation above), squared and averaged over the recorded tokens:

\[ \text{MSE in } \mathbf{Y} = \text{mean}\Big[\big((\hat w - w)\cdot x\big)^2\Big] = (\hat w - w)^2 \cdot \text{mean}\big(x^2\big) \]

The two forms are equal because \(\hat w - w\) is the same on every token. So a weight's MSE in \(\mathbf{Y}\) is large only if it is stored wrong and its input is large. A row's MSE in \(\mathbf{Y}\) is the sum over its weights. Each weight is measured on its own, as if it were the only wrong weight, so this cannot see errors from different weights cancelling each other.

Row \(k\) alone holds 71% of the matrix's total MSE in \(\mathbf{Y}\); no other row holds more than 6%.

In one sentence: the outlier input multiplies weights stored about 5× too large, because the format has nothing that small.

3. Fix 1: Choose the scale so row \(k\)'s weight fits

How a weight is stored. Each column of \(\mathbf{W}\) is cut into groups of 32 weights that share one scale \(\Delta\). Each weight is stored as one of 8 levels times \(\Delta\), four positive and four negative, with no level at zero. GPTQ sizes \(\Delta\) for the group's largest weights. Row \(k\)'s weight is far smaller than those, so it falls below the smallest level and is rounded up to it.

Fix 1 touches only the groups that hold a weight of row \(k\), one per output channel. For each of those groups it picks a new \(\Delta\), then re-rounds the group's weights under it:

  1. Fit row \(k\)'s weight. Each of the four levels with the weight's sign gives one \(\Delta\) that puts the weight exactly on that level.
  2. Spare the rest. Of those four, keep the \(\Delta\) that rounds the other 31 weights closest to their NVFP4 values.
  3. Store \(\Delta\). Scales are stored in 8 bits, so \(\Delta\) is rounded too, and the weight ends up slightly off.

The example weight goes from 5× too large to about 2% off. The fix uses only the NVFP4 weights and the format, no data.

What fix 1 changes in \(\mathbf{W}\). Rows are input channels, columns output channels. Fix 1 gives a new \(\Delta\) to one group per output channel: the group that holds row \(k\)'s weight.

The price. The new \(\Delta\) is smaller, so most of the other weights in the group are now too large and are clipped to the largest level. That costs little, because their inputs are tiny: the group's MSE in \(\mathbf{Y}\) still falls sharply.

Close to AWQ. Fix 1 rests on the same idea as AWQ2: a weight that multiplies a large input matters most, so it should be stored well. AWQ builds this in before quantizing, by rescaling input channels using calibration data. The agent arrived at it on its own, after GPTQ had already run, using only the inputs it recorded in step 2 and the NVFP4 weights.

4. Fix 1 exposes GPTQ's compensation; fix 2 removes it

Fix 1 has a side effect, in other rows of the same matrix.

GPTQ's compensation. GPTQ quantizes \(\mathbf{W}\) one row at a time. After each row, it adjusts the rows it has not quantized yet so that, on its calibration text, they cancel as much as they can of the error it just made in \(\mathbf{Y}\). Usually these adjustments are small. For row \(k\) they are not: the outlier input makes its error in \(\mathbf{Y}\) large, so GPTQ cancelled most of it with large adjustments to some later rows. We call these the compensating rows, and the adjustments their compensation.

Fix 1 removes almost all of row \(k\)'s error. The compensation then has little left to cancel, and becomes error in \(\mathbf{Y}\) itself.

What fix 2 changes in \(\mathbf{W}\). Illustration. GPTQ quantizes the rows from top to bottom. The compensating rows (hatched) sit scattered after row \(k\).

Finding them needs no data. For each row, the agent compared how far GPTQ's weights are from NVFP4 with how far plain rounding to the nearest level would be, under the same scales. In a typical row the two are about equal. In a compensating row GPTQ's weights are several times farther, because they carry the compensation. The agent marked those rows as compensating rows: a small fraction of all rows.

Fix 2 keeps every scale and re-rounds the compensating rows from their NVFP4 values to the nearest level. That removes the compensation. All other rows keep GPTQ's values.

Neither fix adds storage, so the checkpoint's size and speed are unchanged.

Conclusion

Weight-space programming is already useful for quantization. Given a broken 3-bit checkpoint and its NVFP4 source, an agent found what GPTQ got wrong and fixed it by editing about one weight in 120,000, with no calibration data and no training. On the poorly calibrated checkpoint, that closed ~80% of the gap to NVFP4 on every benchmark. The edits only rewrite existing levels and scales, so the model keeps its size, format and kernels.

Longer term, we see this going much further. As LLMs get more capable, we expect agents, or rather swarms of them working in parallel, to quantize models with trillions of parameters themselves, starting from the full-precision weights, instead of only repairing a checkpoint after the fact.
